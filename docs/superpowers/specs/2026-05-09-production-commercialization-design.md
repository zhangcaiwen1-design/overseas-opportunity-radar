# 海外商业机会雷达生产上线与商业化设计稿

## 目标
把当前已经具备采集、选稿、生成、推送能力的 overseas-opportunity-radar，升级为一个可持续生产运行、可对外发布、可承接商业化转化的内容业务系统。

它不再只是“每日推送后台”，而是：
- 一个可上线的生产运行平台
- 一个内容生产与分发中枢
- 一个以网站为核心承接商业化的产品系统

## 核心结论
推荐路线不是“三端并行平均发力”，而是：
1. **网站作为主阵地**
2. **公众号作为二次分发与私域沉淀渠道**
3. **抖音作为增长实验渠道**

推荐先做 **标准生产上线**，而不是最小上线，也不是一开始就做重型多环境平台。

## 背景
当前项目已经具备较完整的内容链路能力：
- 定时/手动采集候选信号
- 候选筛选与推荐决策
- 精选内容生成
- `push_digest` / `push_decision` / `push_execution` 产物沉淀
- 今日工作台、历史记录页、设置页
- Feishu / WeCom / WxPusher 推送链路
- 基于 Supabase Postgres + Storage 的数据与产物存储

最近已经重点修完一批上线前必须收口的一致性问题：
- 同一个 run 的重选、重生、重推不再继续展示旧结果
- 旧 DB 记录与旧 Storage 对象可同步清理
- 工作台与历史聚合不再重复或错挂旧 run 数据

因此，当前项目已经从“功能尚未串起来”的阶段，进入“业务链路能跑，但缺少生产化与商业化外层结构”的阶段。

## 一期定位
一期不是做完整媒体平台，不是做多角色 CMS，也不是做完全自动化无人值守机器。

一期的目标是：
1. 每天稳定产出可用内容
2. 网站能够对外承接流量与转化
3. 公众号能够做稳定二次分发
4. 运营者能够发现异常、补跑任务、审核发布
5. 商业化入口能先跑起来

## 范围
### 范围内
- 生产环境部署与运行架构定稿
- staging / production 环境隔离
- 定时任务、运行追踪、失败告警、人工补跑
- 网站主发布链路
- 公众号二次分发链路
- 抖音脚本/标题/封面文案输出链路
- 商业化承接页与转化入口
- 运营后台、发布台、告警恢复台
- 审计与操作留痕

### 范围外
- 多租户 SaaS
- 复杂团队权限系统
- 自动化抖音正式发布
- 全自动公众号无人审核发布
- 大规模推荐算法平台化
- 完整 BI 数据仓库
- 成熟广告投放系统

## 推荐方案比较

### 方案 A：最小生产上线
内容：Vercel 部署、Supabase 生产库、真实 cron、基础告警、手动补跑。

优点：
- 最快上线
- 工程改动最少

缺点：
- 只能算“能跑”
- 运营与恢复能力偏弱
- 很快又会回到持续补洞

### 方案 B：标准生产上线（推荐）
内容：
- 方案 A 的全部能力
- 运行健康面板
- 失败可恢复机制
- 人工审核发布口
- 操作审计
- 网站商业化承接能力
- 公众号稳定分发能力

优点：
- 能真正支撑内容业务开始跑
- 兼顾速度与稳定性
- 最符合当前项目成熟度

缺点：
- 比最小上线多一轮设计与实现成本

### 方案 C：强化生产上线
内容：
- 方案 B 的全部能力
- 更完整的多环境发布门禁
- 更重的监控与成本治理
- 更完整的自动重试与值班体系

优点：
- 最稳

缺点：
- 过重
- 对当前 MVP 阶段来说投入过大

## 推荐总路线
采用 **方案 B：标准生产上线**。

总路线分成 4 层：
1. **生产运行层**
2. **内容生产层**
3. **分发渠道层**
4. **商业化层**

并按以下业务策略推进：
- **网站首发**：内容资产与转化中枢
- **公众号分发**：稳定触达与私域沉淀
- **抖音实验**：脚本和素材输出，先不自动发布

## 整体产品架构

### 1. 信号层
职责：
- 从 GitHub、HN、Reddit、RSS 等来源采集原始机会信号
- 去重、标准化、排序
- 形成每日候选池

输入：原始来源信号
输出：`candidates`

### 2. 编辑层
职责：
- 给候选打分与排序
- 给出推荐候选、推荐渠道、风险说明
- 形成 AI 可审的编辑建议

输入：候选池
输出：`push_decision`、推荐列表、风险摘要

### 3. 内容层
职责：
- 生成网站长文主稿
- 派生公众号图文稿
- 派生抖音脚本、口播提纲、标题、封面文案
- 输出内容产物并入库存档

输入：精选候选
输出：内容产物、分发稿件

### 4. 分发层
职责：
- 网站发布
- 公众号发布
- 抖音脚本与素材导出
- 推送执行记录

输入：已审核或可发布稿件
输出：站内内容、渠道记录、分发日志

### 5. 商业化层
职责：
- 通过网站完成 SEO 承接
- 通过订阅、私域、咨询、合作形成转化
- 逐步扩展到会员、社群、广告或联盟分成

输入：外部流量
输出：转化行为

### 6. 运营层
职责：
- 看运行状态
- 审核内容
- 手动补跑
- 告警处理
- 审计追踪

输入：运行日志、发布状态、异常结果
输出：人工决策与恢复动作

## 生产上线架构

### 技术栈推荐
- **Next.js** 继续作为后台与网站应用主体
- **Vercel** 负责 Web 部署
- **Supabase Postgres** 负责业务数据
- **Supabase Storage** 负责内容与产物对象
- **Vercel Cron** 负责每日调度入口；只有在后续需要更强重试、排队或观测时，才升级到外部调度器

原因：
- 与当前项目结构最贴合
- 切换成本最低
- 便于快速进入生产运行状态

### 环境策略
至少维护两个环境：
- `staging`
- `production`

要求：
- 两套 Supabase 项目
- 两套 Storage bucket
- 两套环境变量和 secrets
- 两套定时任务
- 禁止 dev 直接连 production

### 运行链路
生产环境中的标准执行顺序：
1. cron 触发每日采集
2. 生成 run 与候选池
3. 形成推荐决策
4. 运营者审看推荐与内容
5. 生成网站主稿及分发稿
6. 网站发布
7. 公众号二次分发
8. 产出执行日志、推送日志、发布状态

### 生产保障原则
每一次 run 都必须具备：
- 可追踪
- 可复盘
- 可补跑
- 可审计
- 幂等重试不污染当前视图

### 后续扩展边界
第一阶段不引入独立 job queue / worker 系统。
若后续出现明显长任务瓶颈，再把重任务拆到单独执行层。

## 内容发布架构

### 网站
网站是内容资产中心，也是商业化主阵地。

网站需要承载：
- 每篇机会主稿页
- 每日精选页
- 专题聚合页
- 基础 SEO 元信息
- 订阅、社群、咨询、合作入口

发布策略：
- 第一阶段采用“自动成稿 + 人工确认发布”
- 不在一开始做完全自动发布

### 公众号
公众号作为二次分发层。

职责：
- 从网站主稿派生图文版
- 做稳定二次传播
- 把用户沉淀到私域

策略：
- 保留人工审核口
- 不做完全无人值守自动发文

### 抖音
抖音第一阶段只做增长实验，不做生产主渠道。

输出内容包括：
- 短视频脚本
- 口播提纲
- 标题建议
- 封面文案
- 可复用素材建议

策略：
- 先人工发布
- 先验证哪类选题有效
- 暂不做自动分发

## 商业化架构

### 承接中枢
网站承担全部商业化承接责任。

网站需要具备的转化模块：
- 邮件/表单订阅
- 微信或社群引导
- 咨询入口
- 商务合作入口
- 后续会员/社群升级位

### 转化优先顺序
推荐优先级：
1. **订阅**
2. **私域沉淀**
3. **咨询服务**
4. **会员/社群**
5. **广告/联盟分成**

### 渠道角色定位
- **网站**：资产沉淀与转化
- **公众号**：稳定分发与复访
- **抖音**：拉新增量与品牌曝光

## 运营后台设计

### 1. 今日工作台
职责：
- 查看当前 run 状态
- 查看候选、推荐、成稿、分发结果
- 一键补跑采集 / 生成 / 推送 / 发布

### 2. 历史运行页
职责：
- 查看每次 run 的完整链路
- 查看失败位置
- 查看产物、分发记录、告警结果

### 3. 内容发布台
职责：
- 查看网站稿、公众号稿、抖音脚本
- 审核、修改、发布、撤回

### 4. 渠道配置页
职责：
- 管理网站域名与发布设置
- 管理公众号配置
- 管理抖音脚本导出参数
- 管理 OpenAI / webhook / 业务变量

### 5. 告警与恢复页
职责：
- 查看最近失败任务
- 查看失败原因
- 查看恢复建议
- 执行人工补跑

## 自动化边界

### 可以自动的部分
- 采集
- 筛选
- 推荐决策
- 成稿生成
- 产物上传与记录
- run 状态记录

### 第一阶段保持半自动的部分
- 网站正式发布
- 公众号正式发布
- 抖音正式发布

结论：
**生成自动化，发布半自动化。**

原因：
- 商业化早期更怕发错内容，而不是发慢一点
- 发布口保留人工阀门，更符合当前业务阶段

## 数据与领域扩展建议
在现有 `runs / candidates / selected_items / artifacts / push_logs / push_configs` 基础上，建议逐步扩充以下领域对象：

### `content_variants`
记录同一内容在不同渠道的派生版本。

字段建议：
- `id`
- `run_id`
- `candidate_id` 或 `selected_item_id`
- `channel`：`site` / `wechat` / `douyin`
- `title`
- `body`
- `status`：`draft` / `reviewed` / `published` / `failed`
- `published_at`
- `review_notes`

### `publication_logs`
记录每次外发或发布动作。

字段建议：
- `id`
- `content_variant_id`
- `channel`
- `action`：`publish` / `retry` / `withdraw`
- `status`
- `response_summary`
- `operator`
- `created_at`

### `lead_events`
记录商业化转化事件。

字段建议：
- `id`
- `source_channel`
- `page_type`
- `event_type`：`subscribe` / `consult` / `community_join` / `partner_inquiry`
- `created_at`

## 告警与恢复设计

### 告警触发条件
第一阶段建议覆盖：
- cron 未按时执行
- collect 失败
- generate 失败
- push 失败
- publish 失败
- Storage 或数据库不可用

### 告警输出
至少支持：
- 管理后台可见异常列表
- 站内状态提示
- 外部通知渠道（建议先用现有推送链路中的一个内部告警通道）

### 恢复动作
后台应支持：
- 重新采集
- 重新生成
- 重新推送
- 重新发布
- 查看上一次失败原因

## 安全与权限原则
第一阶段不做复杂 RBAC，但必须遵守以下原则：
- 所有管理动作必须带管理员密钥或等价受保护入口
- 生产环境 secrets 不回显
- 发布与推送动作都要有操作留痕
- staging 和 production 数据严格隔离

## 实施顺序

### Phase 1：生产可运行
目标：让系统每天稳定跑起来。

包含：
- production / staging 环境落地
- 真实 cron
- deploy 流程
- env / secrets 管理
- 健康检查
- 告警
- 补跑入口

### Phase 2：网站上线
目标：让内容站真正对外承接流量与转化。

包含：
- 网站文章页
- 每日精选页
- 专题聚合页
- SEO 基础
- 订阅与转化入口
- 发布审核口

### Phase 3：公众号分发
目标：形成稳定二次分发链路。

包含：
- 主稿转公众号稿
- 发布审核
- 发布记录
- 渠道表现回看

### Phase 4：抖音增长实验
目标：验证短视频是否值得成为长期获客渠道。

包含：
- 脚本生成
- 标题与封面文案
- 素材输出
- 人工发布工作流

### Phase 5：商业化增强
目标：开始稳定变现。

包含：
- 订阅体系
- 私域沉淀
- 咨询转化
- 社群/会员
- 广告或联盟分成

## 验证策略

### 设计级验证
- 每个 run 是否可追踪、可补跑、可审计
- 内容是否能一稿多端派生
- 网站是否承担商业化承接中枢
- 渠道职责是否清晰分层

### 上线前验证
- staging 完整演练 daily run
- 故障场景演练：collect fail / generate fail / push fail / publish fail
- 补跑链路演练
- secrets 与生产环境隔离检查
- 手工审核与发布流程演练

## 最终建议
真正应该切换的主线不是继续零散补 UI，而是：

> **Phase 1 生产运行层 + Phase 2 网站上线层 联合推进**

即先把系统做成一个稳定能跑的生产平台，同时把网站作为正式对外产品上线。

实施计划上把这两层视作同一个首发里程碑：先打通 staging 演练与 production 运行闭环，再接网站文章页、精选页与转化入口上线。

这会是当前项目从 MVP 走向真实业务系统的关键转折点。
