# 精选成稿结构重设计稿

## 目标
把当前“模板式摘要稿”升级为真正可读、可发、可拆解的精选案例稿。每篇稿子都要清楚回答：这个项目是什么、它怎么运作、为什么值得看、放到国内怎么改、怎么开始卖。

## 背景问题
当前精选成稿虽然已经能生成 Markdown 和 HTML，但内容结构过于单薄，主要问题有：

- 缺少明确的项目名称展示策略，很多文章只剩英文仓库名
- 缺少“项目介绍”与“运作模式”这两个核心板块
- 国产化路径、变现方式、验证路径目前仍是通用模板句，几乎所有项目都相同
- 输出更像摘要卡片，而不像真正的项目拆解稿

这与目标中的“国产化机会拆解、协作方式分析、落地与变现实操”不匹配。

## 本次设计范围
范围内：
- 重设计精选文章的数据结构
- 重设计精选 Markdown/HTML 的章节结构
- 新增项目分析层，避免继续直接套模板生成文案
- 让不同项目类型输出不同重心的文章内容
- 允许“验证步骤”成为条件性板块，而不是固定必有板块

范围外：
- 机会池 `pool/*.html` 的结构改版
- 每日合集视频脚本升级
- 评分与筛选逻辑调整
- 推送渠道与推送格式改造
- 素材抓图能力本身

## 设计目标

### 1. 每篇精选稿必须先把项目说清楚
必须能明确看出：
- 项目名称
- 项目一句话介绍
- 项目介绍
- 运作模式 / 协作方式

### 2. 国产化与变现必须变成项目定制内容
不能继续使用对所有项目都一样的句子。至少要让以下段落产生明显差异：
- 运作模式 / 协作方式
- 为什么值得看
- 国产化路径
- 变现实操

### 3. 宁可少一段，也不要套话
“验证步骤”默认不是固定必选板块。只有当某个项目确实能产出具体、差异化、可执行的验证动作时才展示，否则直接省略。

### 4. 先做精选稿，不扩散到其他产物
本次只把精选稿改扎实，不同时拉上机会池和视频一起复杂化。

## 精选稿标准结构
精选稿默认采用以下 8 个固定主板块：

1. 项目名称
2. 一句话介绍
3. 项目介绍
4. 运作模式 / 协作方式
5. 为什么值得看
6. 国产化路径
7. 变现实操
8. 内容传播角度

可选板块：
9. 验证步骤（仅当内容具体且不重复时才输出）

### 顺序设计理由
- 前 3 段先解决“这是什么项目”
- 第 4 段解释“它怎么跑起来”
- 第 5 段解释“为什么值得现在看”
- 第 6、7 段落到“国内怎么做、怎么卖”
- 最后一段把它转成可发的公众号 / 抖音内容角度

## 各板块写法要求

### 项目名称
- 保留原始英文名
- 如英文名不直观，可补充中文解释名
- 标注来源平台（GitHub / RSS / Reddit 等）
- 标题不应只剩仓库名本身，应该具备可分发性

### 一句话介绍
必须至少包含三个信息：
- 谁在用
- 解决什么问题
- 最后得到什么结果

禁止只写功能标签式短句。

### 项目介绍
要回答：
- 这个项目本质上是什么
- 核心能力是什么
- 它不是什么，避免误判

也就是说不只解释“是什么”，还要解释“不要把它理解成什么”。

### 运作模式 / 协作方式
必须写成链路，不能写成泛概括。优先覆盖：
- 参与角色
- 输入内容
- 中间处理过程
- 输出结果
- 闭环方式

如果项目本身不是多人协作系统，也要至少写清楚“用户动作流”。

### 为什么值得看
必须结合项目特征说明至少 2-3 个判断点，例如：
- 海外已经出现真实使用需求
- 国内有相似但未被很好满足的链路
- 可以轻量验证，不必重投入
- 竞争不一定低，但可以通过切口变化进入
- 有细分、闷声赚钱或低竞争机会

### 国产化路径
必须写“改造动作”，不能写空泛的“适合本地化”。优先分析：
- 渠道替换
- 支付替换
- 协作方式替换
- 获客入口替换
- 功能删减与重新打包

### 变现实操
必须像一个小商业方案，而不是几种收费名词列表。至少要说明：
- 卖给谁
- 先卖什么最小版本
- 怎么收费
- 靠人工交付还是工具交付
- 第一批客户可能从哪里来

### 内容传播角度
要把案例转成可发布内容，而不是重复正文。至少应输出：
- 公众号可讲的切入点
- 抖音可讲的切入点
- 更适合强调项目机会、协作模式还是国产化改造

### 验证步骤（可选）
默认不出现。只有在能明确写出差异化、具体、可执行动作时才输出。若只能写出高重复度套话，则整段省略。

## 项目分型规则
为了避免所有项目都写成同一套话术，精选稿生成前必须先分型。当前建议分为 4 类：

### A 类：工具增强型
定义：解决单点效率问题的工具能力。

重点写法：
- 项目介绍：替代了什么手工动作
- 运作模式：输入 → 处理 → 输出
- 国产化路径：如何接入微信、企微、社群或本地文件流
- 变现实操：更偏代处理服务、模板包、轻工具

### B 类：工作流协作型
定义：强调角色分工、流程衔接和组织方式的系统。

重点写法：
- 运作模式 / 协作方式
- 为什么值得看：可复制的是流程，不只是功能
- 国产化路径：如何接入企微、飞书、微信群、表单、私域
- 变现实操：更偏代搭建、咨询、陪跑、行业版 SOP

### C 类：业务前台型
定义：更接近直接面对客户的业务产品雏形。

重点写法：
- 项目介绍：服务什么经营场景
- 运作模式：获客 → 转化 → 交付 → 复购
- 国产化路径：重点写渠道、支付、客服、交付替换
- 变现实操：重点写成交方式、客单价、第一批客户来源

### D 类：能力底座型
定义：偏底层基础设施，本身不是最终业务，但能支撑上层产品。

重点写法：
- 项目介绍：它不是终端产品，而是能力底座
- 为什么值得看：它意味着哪些低成本封装机会
- 国产化路径：选细分场景做二次包装
- 变现实操：更偏行业解决方案、二次封装、内部工具交付

## 内容生成分层
当前链路大致是：
`OpportunitySignal -> toWrittenOpportunity() -> Markdown/HTML`

本次应改成三层：

### 第一层：原始信号层
保留现有 `OpportunitySignal` 作为原材料输入。

### 第二层：项目分析层
新增一层“项目分析结果”，至少应包含：
- projectLabel
- projectType
- oneLiner
- projectIntro
- operationModel
- whyItMatters
- chinaAdaptation
- monetizationExecution
- contentAngles
- validationPlan（可选）

这层负责真正的项目判断与内容生成，不允许再直接回退成统一模板句。

### 第三层：渲染层
Markdown 和 HTML 渲染器只负责把分析结果按章节结构排出来，不再承担“思考项目该怎么写”的职责。

## 标题展示策略
精选稿标题建议采用：
- 主标题：中文解释名 / 原项目名
- 副标题：一句话点明这是什么机会

如果当前渲染器只支持单标题，也应至少让主标题具备“人能看懂”的解释性，而不是裸仓库名。

## 实施边界
本次改造仅针对精选稿：
- 精选文章的数据结构
- 精选文章分析层
- 精选 Markdown/HTML 输出
- 对应测试
- 必要的 README 说明

不改：
- 机会池结构
- 视频脚本
- 评分与筛选
- 推送通道
- 素材抓图机制

## 验收标准

### 1. 三类不同项目生成后，重点段落必须明显不同
至少验证工具增强型、工作流协作型、能力底座型三类项目，确保以下段落存在真实差异：
- 项目介绍
- 运作模式 / 协作方式
- 为什么值得看
- 国产化路径
- 变现实操

### 2. 每篇稿子都必须补齐核心信息
至少必须出现：
- 项目名称
- 项目介绍
- 运作模式 / 协作方式

### 3. 国产化路径必须是动作化内容
如果只剩“适合本地化落地”这种空句，则不算通过。

### 4. 变现实操必须可落地
至少能看出卖给谁、卖什么、怎么收费、怎么交付、客户从哪里来。

### 5. 验证步骤允许缺省
如果没有足够具体内容，不出现是正确行为，不视为缺失。

### 6. 渲染结果仍需完整可读
Markdown 与 HTML 输出必须：
- 标题顺序清晰
- 无空章节标题
- 无 `undefined`、空白占位或残缺段落
- 在可选板块缺失时仍保持版式自然

## 为什么这套方案更接近目标
因为用户真正需要的不是“每天出几篇看起来像文章的东西”，而是能拿来判断机会、讲清协作逻辑、拆解国产化路径、支持实际分发的案例稿。

只有把精选稿从“模板摘要”升级成“结构化案例拆解”，后面的：
- 公众号发布
- 抖音内容改写
- 每日合集视频脚本
- 商业机会判断

才会有可靠的内容底座。

## 下一步实施方向
下一步实施计划应围绕四件事展开：
1. 扩展精选稿数据结构与分析结果模型
2. 新增项目分型与项目分析层
3. 更新 Markdown / HTML 渲染器的章节结构
4. 增加差异化回归测试，确保不再生成统一模板文案
